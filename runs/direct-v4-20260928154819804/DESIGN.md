# Folio — design record

## Before implementation

The brief, CONTRACT.md, CAPABILITIES.md, and all five selected skill entrypoints were read before presentation changes. The hook owns conversations, drafts, attachments, tool activity, and recovery. This record concerns the presentation only.

### Approaches considered

1. **Document workbench:** a three-column layout with history, conversation, and a permanent source inspector. This would give documents prominence, but the supplied API exposes attachment metadata rather than document contents. A permanent inspector would spend space on very little information or imply unsupported inspection.
2. **Question launcher:** a centered input and a compact history popover at every width. This would give the welcome screen a strong focal point, but revisiting existing work would require an extra action every time. Modern Interface Craft explicitly recommends a persistent desktop history rail for Folio.
3. **Research desk — selected:** persistent, filterable history alongside an open reading column; a soft input surface is the principal manipulated object. No cards around prose, invented source previews, or marketing introduction. On small screens, history becomes an anchored, nonmodal disclosure. This makes starting, reading, and revisiting the primary hierarchy.

The selected direction is a design judgment, not a measured usability claim.

### Composition committed before coding

- **Alignment:** a left-aligned reading column, up to 48rem wide, shared by questions, answers, and input. Desktop navigation is a separate 17rem rail on the same white canvas.
- **Primary silhouette:** a moderately rounded, softly filled rectangle. The quiet state holds the invitation; focus, text, files, and running work reveal relevant controls. One stable textarea persists across states.
- **Navigation cost:** one click to a visible desktop conversation; open then select on mobile. Filtering uses only real titles from the hook.
- **Type:** locally bundled Manrope, ordinary UI at 1rem/1.5 and weight 500, secondary information distinguished by tone. A wordmark, input invitation, and real Markdown headings are the intentional exceptions.
- **Object continuity:** file IDs and filenames survive the move from pending attachments to the submitted question. Local position animation acknowledges addition/reflow; removal mutates the hook immediately. Send and stop occupy the same action position.

### Limits and conflicts

- The shared behavioral contract takes precedence over presentation guidance. No new conversation, attachment, or response state is fabricated or duplicated.
- Motion Storytelling changed the continuity decision and status sequencing. Its film duration, soundtrack, characters, and narration did not influence the product: this is a research application, not an explainer.
- Apple Design's glass-material recommendation and system-font default yield to the selected art direction. Its gesture momentum, rubber-banding, and velocity projection are not applicable because Folio has no custom drag/snap interaction. File drop uses native drag events and a keyboard-accessible picker.
- No optional dark theme, unsupported source viewer, rename, export, or settings surface is added.
- No browser evidence has been supplied in this initial implementation session. Browser-informed critique and verification must be reported separately from these design intentions.

## Implementation-session review

- Presentation components are in `src/ChatParts.tsx`; the application layout, navigation coordination, and sole `useChat()` call are in `src/App.tsx`. Styles and centralized semantic color tokens are in `src/styles.css`.
- The empty input's vertical space uses a viewport-relative basis so revealing its toolbar expands downward without shifting its first line. The same textarea remains mounted when the input becomes the conversation dock. Only its wrapper's position is animated; glyphs are not scaled.
- The mobile history opens with focus on its close control, avoiding an unsolicited software keyboard. It dismisses on Escape, outside pointer interaction, or focus leaving the disclosure. Selection focuses the conversation heading; New chat intentionally focuses the input. Closing makes the panel inert immediately while its spring retargets.
- Completed activity retains its expanded footprint until the reader chooses to collapse it. This intentionally avoids an automatic collapse that would move the answer while being read. The summary changes with the actual hook state; labels remain mounted. A concise live region announces stage/completion changes instead of streaming every token.
- Source review caught a CSS-layer conflict: an unlayered icon-button display rule would override Tailwind's responsive hiding. Display now lives in the components layer. This was source reasoning, not a browser finding.
- Conversation-row focus rings are inset to avoid clipping inside their scroll container. Clear-search and attachment-removal actions restore focus to a stable input.
- Independent navigation rows and the code block use the secondary 12px shape family; they are not claimed to be concentric with the distant mobile panel boundary. The calculated composer inset relationship is the primary nested geometry.

## Design refinement 1 — critique before changes

Read the presentation source, contract, capabilities, existing ledger, and all five selected skill entrypoints again. Reviewed all ten supplied screenshots/contact sheets. The report records no viewport overflow, runtime errors, or automated accessibility findings; it also reports a visible retry control after cancellation and a visible composer with reduced motion. These findings describe the previous implementation, not this revision.

Three weaknesses take priority:

1. **Incomplete-looking mobile data.** `mobile-research.png` presents Priority and Next step, with Owner entirely outside the visible table. The source forces a 29rem minimum table width. The table is keyboard-focusable and horizontally scrollable, but there is no visible explanation that more columns exist. The code block later in `interaction-mobile.png` has a similar discovery problem. Desktop and intermediate tables already read well.
2. **A moving control crosses newly arriving work.** The entry textarea is a useful focal point in `desktop-welcome.png`, `intermediate-welcome.png`, and `mobile-welcome.png`. However, the send sequence in `interaction-mobile.png` samples the composer partway over the activity area, with response status below it. Source confirms that the same input wrapper travels from the entry position to the bottom dock. The screenshots establish the large displacement and intermediate overlap; they do not establish animation smoothness or duration. Preserving the node alone was not enough to give this transition useful spatial continuity.
3. **Incidental controls change the reading viewport.** The previous working composer switches between a 64px quiet surface and a taller toolbar state on focus. Source also adds file guidance below it after opening the picker, then removes it on send. This makes the available reading height depend on focus/help rather than the document. The earlier repair already identified a related recovery-target problem. The populated captures show a quiet dock, whereas the interaction sheets show its expanded state; they do not prove a missed click in the current build.

Retain the unboxed reading column, direct desktop conversation access, modest Manrope hierarchy, semantic palette, and 20px/8px/12px input geometry. The attachment capture has coherent inset channels and readable filename/size. The visible tool steps explain actual hook progress without animation on streamed glyphs. Extra welcome copy, invented work, a colored navigation panel, and a new decorative identity would not address these weaknesses.

## Design refinement 2 — critique before changes

Re-read the source, contract, capabilities, this record, and all five selected skill entrypoints. Re-read Modern Interface Craft's `light-workspace.md` and `interaction-recipes.md` for the input and reading-state decisions. The supplied report records no overflow, runtime errors, or automated accessibility findings in the previous build. The visible retry after cancellation and composer under reduced motion confirm those particular observed states; they do not cover all keyboard paths.

The three most consequential weaknesses in this implementation are:

1. **The working input spends too much of a small reading viewport on an empty second row.** In `mobile-research.png`, the 112px two-row composer plus its clearance leaves the table's final row below the view. `intermediate-research.png` ends with a sliver of the code surface. Reserving the toolbar in refinement 1 correctly stabilized focus/retry targets, but did not require a full-width toolbar under a one-line follow-up. This is a composition tradeoff, not reported viewport overflow or inaccessible content.
2. **Continuation and returning to a reading position are weak.** The settled research captures end partway through actual content without an explicit continuation action. Source shows that the existing floating “Latest response” button is measured only after scrolling, and conversation selection always resets to the top. The contact sheets show the response's recommendation and copy action farther down, so the first viewport is not the whole answer. Those sheets do not demonstrate whether users discover the remaining content, and do not show a round trip to a partly read thread.
3. **Progress repeats itself before there is an answer.** Both interaction sheets show “Preparing your response” and “Writing response” simultaneously, beneath the actual tool stages. These labels describe one phase as two separate blocks, take reading space, and cause a block to disappear when text arrives. Keep the actual stages, but give response preparation/writing one consistent status location.

Preserve the quiet invitation in the three welcome captures, direct desktop history, the white reading surface, readable medium-weight type, native Markdown hierarchy, and the mobile table's now-visible Owner column. `mobile-attachment.png` supports the current inset relationships. The supplied evidence confirms that the immediate send placement no longer samples a composer crossing the answer; it cannot establish smoothness. No new decorative treatment is needed.
